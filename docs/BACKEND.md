## 1. What runs where

Nothing runs on a server that this project operates. There are three places
code executes, and only one of them is live.

| Where | When | What |
|---|---|---|
| GitHub Actions | Weekly, and on demand | The whole pipeline: acquisition, analysis, validation, export, build, release, email. |
| Supabase | Live, from the browser | Sign-in and saved alert rules. The only runtime backend. |
| GitHub Pages | Live, static | Serves the built page. No server-side execution. |

Analysis stages are guarded individually. A stage that fails records the
failure and leaves its table empty rather than aborting the run or substituting
a value. Optional enrichment stages are off unless explicitly enabled, so they
cannot silently change a published figure.

### 3.2 The validation gate

The export step runs the gate. A blocking failure stops the job, so no site
update, no release and no email follow, and the previous week stays published.
A non-blocking discrepancy publishes with the gate marked `PASS_WITH_WARNINGS`
and the discrepancy listed on the Audit log.

This is the single most important property of the system: **a run that cannot
do its job publishes nothing rather than publishing something wrong.**

## 5. Automation

`.github/workflows/weekly-update.yml` - runs on the schedule `17 13 * * 6` and on demand from the **Run workflow** button.

| Step | Purpose |
|---|---|
| **actions/checkout@v5** | Copies the repository onto the clean machine. This is why a push must precede a run: the machine takes what is on GitHub, not what is on your computer. |
| **Verify the build inputs are present** | Checks that the pipeline, the export and build scripts, the template and the requirements file are all present and non-empty. A missing input fails the run here rather than being worked around later, so the previous week stays published. |
| **actions/setup-python@v6** | Installs the pinned Python version. |
| **Install packages** | Installs everything in `requirements.txt`. |
| **Prepare Colab-style folders** | Recreates the directory layout the pipeline expects and copies `static_inputs/` into place. |
| **Download Census TIGER/Line 2025 counties (too large for GitHub, ~130 MB)** | Fetches the county boundary file fresh each run; at roughly 130 MB it is over GitHub's file limit, so it is not stored. Without it the maps cannot draw. |
| **Set the data window to end on today's date** | Sets the end of the study window to the current date, so each run covers one more week than the last. |
| **Run surveillance pipeline** | The substance of the run, and most of its duration. Pulls the CDC datasets, harmonizes, standardizes, and computes every analytic layer. API keys are injected here only. |
| **Export app data (stops here if validation fails or tables are from mixed runs)** | Builds the entity CSVs **and runs the validation gate**. A hard failure here stops the job, so no site update, release or email follows and the previous week stays published. |
| **Persist the forecast ledger** | Commits the updated ledger back to the repository so it outlives the machine. See 5.1. |
| **Build site** | Renders one export into the finished static site. |
| **Keep this run's export (90 days)** | Attaches the export, tables and full log to the run for 90 days. Runs even on failure, so a failed run can still be diagnosed. |
| **Archive this run as a permanent GitHub Release** | Publishes the permanent GitHub Release. See 5.2. |
| **Email saved alerts (Supabase)** | Sends the weekly alert emails. Marked `continue-on-error`, so a mail failure never blocks the site update. |
| **actions/upload-pages-artifact@v3** | Hands the built site to GitHub Pages. |
| **actions/deploy-pages** | Publishes it. The site is live when this finishes. |

### 5.1 Why the forecast ledger is committed back

The runner is destroyed after each run, so a forecast written during a run
would vanish with it. The workflow commits the updated ledger to the
repository, tagged `[skip ci]`. The value is not the file but the commit
timestamp: git history is the evidence that each prediction was recorded
**before** the week it predicted. Without that, the forecast scoreboard would
be unfalsifiable.

### 5.2 Releases

Every successful run publishes a release tagged `<run_id>-r<run_number>` with
the tables, figures, app export, manifest and full log. CDC revises its data
continuously, so a figure is only reproducible against the release it came
from.

## 6. Secrets

| Secret | Used for |
|---|---|
| `NCBI_API_KEY` | Raises the NCBI rate limit for genome records |
| `SMTP_PASSWORD` | Sends the weekly alert email |
| `SMTP_USER` | Sends the weekly alert email |
| `SOCRATA_APP_TOKEN` | Raises the CDC Socrata API rate limit |
| `SOCRATA_KEY_ID` | Authenticates the CDC Socrata pull |
| `SOCRATA_KEY_SECRET` | Authenticates the CDC Socrata pull |
| `SUPABASE_SECRET_KEY` | Server-side read of saved alert rules |

These exist only as GitHub repository secrets and are injected as environment
variables for the single step that needs them. None appears in the code, in the
built site, in the logs or in any release asset. The Supabase **secret** key is
used only by the server-side mailer; the browser receives the publishable key,
which is public by design.
